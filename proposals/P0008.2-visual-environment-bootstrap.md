# P0008.2: Visual Environment Bootstrap

**Status**: Proposed
**Date**: 2026-09-25
**Depends on**: P0008.1 frozen baseline (`aeea55d`)

## Objective

Replace the current implicit 60-second startup sweep with an explicit visual-environment bootstrap.

At startup, the system must establish a minimal answer to three questions:

1. What physical viewpoints can I observe?
2. Which of those viewpoints have I actually observed?
3. What did those viewpoints visually look like when observed?

The bootstrap must NOT require YOLO, face detection, VLM, or semantic object recognition to decide whether a viewpoint has been observed.

Startup is only the first population of a long-lived Visual Environment capability. It is not a separate startup-only world model.

## Background

Current startup behavior is an implicit timing condition inside `RevisitController`:

- startup lasts approximately 60 seconds;
- a fixed PTZ sweep sequence executes;
- normal Commitment/Revisit behavior is gated;
- completion means only that the timer expired;
- there is no explicit READY state;
- there is no explicit coverage result;
- visual evidence from each visited direction is not represented as a startup environment baseline.

P0008.1 is frozen. Its Commitment, target identity, challenger, SWITCH,
RELEASE/reacquire, Gentle Framing and other behavioral semantics are outside this phase.

Industry PTZ systems provide a mature pattern:

    preset/viewpoint
        → move
        → settle
        → dwell/observe
        → next viewpoint

We borrow this mechanism, not Guard Tour as a product feature.

Visual environment evidence must remain independent from semantic recognition:

    "I observed this view"

does not mean:

    "YOLO recognized an object in this view."

## Design

### 1. Explicit lifecycle

Introduce the minimum explicit runtime startup lifecycle required for:

    INITIALIZING
        ↓
    SURVEYING
        ↓
    READY

Do not build a general-purpose workflow/state-machine framework.

The lifecycle exists to answer:

- whether physical initialization is complete;
- whether startup visual survey owns PTZ;
- whether minimum startup coverage is complete;
- when normal runtime behavior may take ownership.

Perception/cognition do NOT need to be globally disabled during SURVEYING.

### 2. Viewpoint is an observation contract

A viewpoint is not merely a PTZ command.

Conceptually:

    Viewpoint
      - stable identity
      - PTZ pose / spatial reference
      - observation state
      - last_observed_at
      - visual evidence
      - coverage state

The exact persisted/runtime representation should reuse the existing
AnchorManager / spatial abstractions where practical.

Before creating a parallel spatial-map abstraction, inspect whether AnchorManager
can safely serve as the spatial index.

If it cannot, document the concrete incompatibility before introducing another
spatial representation.

### 3. Bootstrap survey protocol

For each bootstrap viewpoint:

    MOVE
      ↓
    SETTLE
      ↓
    OBSERVE
      ↓
    RECORD
      ↓
    COMPLETE

Movement must go through the existing PTZ Motion Layer / ownership mechanism.

Do not restore direct startup PTZ writes.

A viewpoint is not covered merely because a movement command was issued.

Observation must occur after camera movement has settled and must satisfy the
existing valid-observation rule.

### 4. Initial viewpoint selection

First version must be deterministic.

Derive a small set of viewpoints from:

- actual PTZ physical limits;
- camera field of view / meaningful overlap where available;
- existing spatial/anchor representation.

Do NOT blindly preserve the old eight `_SWEEP_SEQUENCE` degree deltas.

Do NOT implement Next-Best-View planning.

If the current system lacks enough calibrated FOV information to mathematically
derive optimal coverage, use a documented conservative fixed bootstrap layout
based on known PTZ limits.

The layout is bootstrap coverage, not a claim of complete geometric coverage.

### 5. Visual evidence

Each successfully observed viewpoint must retain a minimal visual baseline.

First implementation should use the cheapest robust representation already
available in the project or standard image processing.

The contract must permit future replacement by stronger visual descriptors.

Do NOT introduce DINO, AnyLoc, CLIP, a new neural embedding model, or another
external inference service in this phase.

Visual evidence must support at least the future question:

    "Does this view look materially different from the baseline I observed?"

P0008.2 does NOT need to solve that future novelty decision completely.

### 6. Coverage

Coverage and visual novelty are separate concepts.

P0008.2 implements minimum spatial bootstrap coverage.

Conceptually:

    viewpoint observed successfully
        -> covered

    required bootstrap viewpoints covered
        -> minimum coverage complete
        -> READY

Do not create a single combined `environment_score`.

Do not require novelty to converge before READY.

### 7. READY semantics

READY means:

    "The system has enough initial visual reference to begin normal operation."

READY does NOT mean:

- the room is understood;
- every object is identified;
- the environment is static;
- novelty is zero;
- all possible views have been visited;
- a geometric map exists.

Normal runtime must be able to continue updating the same Visual Environment
after READY.

P0008.2 only needs to establish the contract for this continuity; sophisticated
runtime refinement is deferred.

### 8. PTZ ownership

During SURVEYING, bootstrap survey owns behavioral PTZ movement.

After READY, ownership returns to the existing runtime behavior.

Tracking / Revisit / Explore must not independently fight startup survey for
movement ownership.

Reuse Motion Layer arbitration rather than adding scattered
`if startup_phase` checks.

### 9. Failure/degraded startup

Bootstrap must not wait forever for perfect environmental understanding.

Distinguish:

- physical initialization failure;
- viewpoint observation failure;
- incomplete coverage;
- successful minimum coverage.

Define bounded behavior for failed viewpoints.

Do not make transient person/object motion prevent READY indefinitely.

The existing no-Arduino degraded-mode bug may be handled only if the new
lifecycle requires an explicit physical-initialization result to avoid deadlock.
Do not otherwise expand into a ServoPTZ reliability project.

## Boundaries

### Included

- explicit INITIALIZING / SURVEYING / READY lifecycle
- startup PTZ ownership
- deterministic bootstrap viewpoints
- move → settle → observe → record protocol
- minimum spatial coverage accounting
- minimal visual baseline/evidence per observed viewpoint
- reuse/integration with existing AnchorManager where architecturally compatible
- removal/replacement of the current implicit 60-second startup sweep
- telemetry sufficient to inspect bootstrap:
  - lifecycle transition
  - viewpoint visited
  - observation success/failure
  - coverage progress
  - READY transition
- tests for startup lifecycle and coverage semantics

### NOT Included (CRITICAL)

- No changes to P0008.1 Commitment semantics
- No multi-person target identity fix
- No challenger fix
- No SWITCH formula changes
- No RELEASE/reacquire changes
- No Gentle Framing tuning
- No Interest/Mission/Value tuning
- No Scene Graph
- No SLAM
- No 3D reconstruction
- No geometric room map
- No object inventory
- No requirement to identify objects
- No new YOLO behavior
- No VLM-based environment understanding
- No DINO/CLIP/AnyLoc/VPR model integration
- No Next-Best-View planner
- No information-gain optimizer
- No adaptive active-survey strategy
- No novelty-convergence READY gate
- No global `environment_score`
- No long-term environment-learning policy
- No general-purpose lifecycle/state-machine framework
- No resurrection of legacy `EnvironmentScanner`
- No Guard Tour product implementation
- No unrelated dead-code cleanup
- No opportunistic refactor

Active Survey / novelty-driven refinement is explicitly deferred until the
bootstrap contract has been validated on hardware.

## Success Criteria

1. Startup no longer becomes normal merely because 60 seconds elapsed.

2. Runtime exposes an explicit transition:

       INITIALIZING → SURVEYING → READY

3. Startup survey uses deterministic viewpoints and each viewpoint follows:

       move → settle → valid observation → record

4. A movement command alone cannot mark a viewpoint covered.

5. A valid image observation can mark a viewpoint covered even when YOLO,
   Face and VLM recognize nothing.

6. READY occurs when defined minimum bootstrap coverage is satisfied, not when
   visual novelty reaches zero.

7. Visual evidence from each covered viewpoint survives the transition to READY
   and remains accessible to normal runtime.

8. Startup survey and normal tracking/revisit do not simultaneously issue
   competing behavioral PTZ goals.

9. Existing P0008.1 behavior remains unchanged after READY except where removal
   of the old startup gate necessarily changes startup handoff.

10. Tests demonstrate lifecycle, coverage and ownership semantics.

11. Hardware telemetry can reconstruct:

       startup
       → viewpoint visits
       → successful observations
       → coverage completion
       → READY

12. No new semantic vision model, SLAM system, NBV planner, or target-selection
    behavior is introduced.
